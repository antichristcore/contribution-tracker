# Карта системы — Contribution Tracker

## Часть 1. Путь данных

**GitHub API → синк.**
Планировщик (APScheduler) раз в 15 минут (плюс по ручной кнопке «Обновить») дёргает GitHub REST API: `GET /repos/{owner}/{repo}/commits` и `.../commits/{sha}` за статистикой `+добавлено/−удалено`, `GET /repos/{owner}/{repo}/pulls/{number}/reviews` за ревью. Ошибка GitHub не роняет процесс — синк возвращает `{"error": ...}`, доска показывает то, что уже собрано раньше.

**Синк → коммиты и ревью.**
Сырые коммиты и ревью сохраняются per-участник через маппинг `github_username / git_author_email`, без веток и PR — команда коммитит прямо в `main`.

**Коммиты и ревью → привязка к задаче по #id.**
`task_linking.py` ищет `#id` в сообщении коммита. Голая ссылка (`#42`) только привязывает коммит и двигает статус `todo → in_progress`. Закрывает задачу лишь ключевое слово **прямо перед** ссылкой (`fixes #42`, `closes #42`, `готово #42`) — как в GitHub, поэтому «Fix login bug #42» ничего не закрывает. Коммит старше даты создания задачи не привязывается (гасит ложные срабатывания на старых issue-номерах). Забытый номер чинится вручную — в карточке задачи есть список «ничейных» коммитов с чекбоксами.

**Привязка к задаче → расчёт вклада (раз в 30 минут).**
`scoring.py` считает `contribution_score = 0.35×norm(строк за 7д) + 0.35×(задач в срок / назначено) + 0.15×norm(ревью) − 0.15×штраф(дней застоя)`, нормализуя строки и ревью относительно медианы, по возможности внутри роли.

**Расчёт вклада → порог (зелёный / жёлтый / красный / нет данных).**
Score и «дней без изменений» сравниваются с порогами (часть 2). Если по участнику вообще нет данных (не привязан GitHub, нет активности) — статус честно «нет данных»: `has_data=false`, `contribution_score=None`, а не молчаливый ноль.

**Порог → уведомление.**
Жёлтый — мягкое персональное напоминание участнику («у тебя 2 задачи без изменений 5 дней, нужна помощь?»). Красный — уведомление тимлиду с конкретикой: имя, задача, число дней без активности.

## Часть 2. Числа и их обоснование

| Число | Значение | Почему именно столько                                                                                                                                                                                                                                                                                   |
|---|---|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Веса: строки / задачи / ревью / штраф | 0,35 / 0,35 / 0,15 / 0,15 | Строки и задачи — два главных объективных сигнала работы, поэтому весят поровну и больше всего. Ревью и штраф за застой — вспомогательные модификаторы, поэтому вес в 2 раза меньше. Строгого расчёта под пропорцию нет.                                                                                |
| Окно активности | 7 дней | Неделя — естественный цикл: достаточно длинная, чтобы не дёргаться от одного пустого дня, и достаточно короткая, чтобы тимлид узнал о проблеме до защиты, а не после.                                                                                                                                   |
| Потолок на один коммит | 1000 строк | Без потолка один коммит на 40 000 строк (сгенерированный файл, миграция, вендоренная библиотека вроде `package-lock.json`) делал автора лучшим в команде — формула не отличает «настоящие» строки от автогенерированных.                                                                                |
| Потолок нормализации | 2× медианы | Без потолка одна аномалия давала `lines_norm = 20` и `score = 7.0` на шкале, которую все читают как 0..1. В команде из 2–3 человек тот же выброс утаскивал медиану так, что правило «на 40% ниже медианы» красило в жёлтый нормальных людей.                                                            |
| Застой → красный | 7 дней | Неделя без движения по конкретной задаче (`tasks_status_stuck_days`) — достаточно долгий срок, чтобы это не было случайностью, и достаточно короткий, чтобы тимлид успел вмешаться до защиты.                                                                                                           |
| Просадка → жёлтый | 5 дней подряд | Серия считается от сегодняшнего дня назад, поэтому один «здоровый» день обнуляет счётчик. Порог ловит устойчивую тенденцию, а не единичный неудачный день.                                                                                                                                              |
| Жёлтый → красный | ещё 3 дня | Это окно на реакцию участника после мягкого напоминания, прежде чем эскалировать тимлиду (итого 5+3 = 8 дней устойчивой просадки до красного). Пропуск в истории (например, синк не отработал) рвёт серию, а не достраивает её до красного — красный гарантированно живая проблема, а не артефакт сбоя. |
| «Просадка» | ниже 60% медианы | Тот же порог, что в коде описан как «на 40%+ ниже медианы». Должен быть заметно ниже нормы (не 90%, под который попадёт полкоманды), но не настолько экстремальным (не 20%), чтобы ловить только крайние случаи.                                                                                        |
| Молчание при открытых задачах | 4 дня | Более простой и грубый сигнал, чем формула score: не про качество работы, а про сам факт присутствия — если задачи висят открытыми и 4 дня вообще ничего не пришло в GitHub.                                                                                                                            |
| Минимум для сравнения внутри роли | 2 человека | Медиана по группе из одного человека — это он сам, поэтому нормализация всегда выродится в 1.0. При <2 людях с данными в роли сравнение откатывается на всю команду, и это явно показывается в интерфейсе (`peer_basis`), чтобы никто не принял такое сравнение за «нормализацию по роли».              |
