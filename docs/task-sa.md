# Задание: Системный аналитик

> **Версия 2.** Первая версия была на восемь задач и требовала матрицу
> трассировки, НФТ и ER-диаграмму. Это выход для промышленного проекта, а не для
> защиты, где оценивают артефакт, который ты объясняешь вслух за минуту.
> Здесь три задачи. Что убрано и почему — в конце файла.

Твой артефакт одной фразой: **правила, по которым система решает, что у человека
проблема, — и обоснование каждого числа в этих правилах.**

Это связующее звено между работой БА и кодом. БА приносит боль тимлида, ты
превращаешь её в правило с конкретными числами, разработка это реализует, девопс
показывает. На защите тебя спросят «почему 0,35?» и «почему семь дней, а не
пять?» — отвечаешь ты.

## P0 — Задача 1. Карта системы и чисел (главная)

**Зачем:** критерий «вклад четырёх направлений» даёт десятку, только если каждый
объясняет свой артефакт **и его связь с соседним**. Это твой артефакт.
Плюс он же готовит ответы на самые вероятные вопросы жюри.

**Сделать: `docs/system-map.md`, одна страница, две части.**

**Часть первая — путь данных.** Схема или список, от источника до человека:

```
GitHub API → синк → коммиты и ревью в базе
                 ↓
          привязка коммита к задаче по #id
                 ↓
       расчёт вклада (раз в 30 минут)
                 ↓
        порог: зелёный / жёлтый / красный / нет данных
                 ↓
     уведомление: жёлтое — участнику, красное — тимлиду
```

По каждой стрелке — одна строка: что происходит и как часто.

**Часть вторая — таблица чисел.** Вот они, из кода. Твоя работа — заполнить
последнюю колонку **своими словами**, а не переписать комментарий из файла:

| Число | Значение | Где | Почему именно столько |
|---|---|---|---|
| Вес строк кода | 0,35 | `W_LINES` | ? |
| Вес задач в срок | 0,35 | `W_TASKS` | ? |
| Вес ревью | 0,15 | `W_REVIEWS` | ? |
| Штраф за застой | 0,15 | `W_PENALTY` | ? |
| Окно активности | 7 дней | `COMMIT_WINDOW_DAYS` | ? |
| Потолок на коммит | 1000 строк | `MAX_LINES_PER_COMMIT` | ? |
| Потолок нормализации | 2× медианы | `NORMALIZE_CAP` | ? |
| Застой → красный | 7 дней | `STUCK_RED_DAYS` | ? |
| Просадка → жёлтый | 5 дней подряд | `YELLOW_STREAK_DAYS` | ? |
| Жёлтый → красный | ещё 3 дня | `YELLOW_TO_RED_EXTRA_DAYS` | ? |
| «Просадка» | ниже 60% медианы | порог риска | ? |
| Молчание при открытых задачах | 4 дня | порог риска | ? |
| Минимум для сравнения по роли | 2 человека | `MIN_PEER_GROUP` | ? |

Три числа обоснованы делом, и это надо знать наизусть:

- **1000 строк на коммит** — без потолка `package-lock.json` на 40 000 строк
  делал автора лучшим в команде. Проверено, потолок поставлен.
- **2× медианы** — одна аномалия иначе ломает шкалу всей команды.
- **Задач не назначено → компонента задач исключается**, а не считается нулём.
  Иначе новичок в первый день теряет 35% ни за что.

Остальные — оценочные. **Так и пиши: «подобрано, не выведено».** По критерию
«ответы и честность» названная самим слабость стоит дороже спрятанной, а
попытка выдать догадку за расчёт — самый дешёвый способ потерять баллы.

**Готово, когда:** объясняешь любую строку таблицы вслух за 20 секунд, без
подглядывания.

**Как защищать:** «Боль тимлида превращается в число вот так. Веса подбирали из
такой логики: код и задачи равны, ревью весит меньше, потому что его меньше по
объёму. Часть чисел подобрана на глаз, и мы это знаем.»

## P0 — Задача 2. Сценарий демо-данных

**Зачем:** сразу два критерия. «Что реально работает» требует сквозного сценария,
воспроизводимого дважды. Экран «До / После» обязателен по `CLAUDE.md`. И то и
другое ломается, если на демо-данных не видно всех состояний сразу.

**Сделать: `docs/demo-dataset.md`** — таблица из пяти участников с точными
числами. Не «примерно активный», а конкретно: сколько коммитов, сколько строк,
сколько задач назначено и сдано, сколько дней застоя, сколько дней молчания.

Требования к набору:

1. На одном экране одновременно видны **все четыре состояния**: зелёный, жёлтый,
   красный и «нет данных». Последнее — обязательно: это наше обещание не
   показывать молчаливый ноль вместо честного «данных нет».
2. Красный приходит **обеими дорогами**: один участник — из-за застрявшей задачи
   (7+ дней), другой — из-за просадки, которая держится 8 дней. Это разные
   правила, и хорошо, когда видно оба.
3. Есть **«застрял»** (коммиты идут, задача стоит) и есть **«забил»** (тишина при
   открытых задачах) — иначе главное отличие продукта от счётчика коммитов не
   показать.
4. Один участник — из роли, где он **единственный** (например, дизайнер). Тогда
   сравнение уходит на всю команду, и интерфейс должен об этом честно написать.
   Проверь, что пишет.
5. Для «До / После»: у одного участника есть **обе точки** — просадка и
   восстановление после разговора с тимлидом. Именно этот человек — герой
   истории на защите.

Числа сверяй с `tests/test_thresholds.py`: там границы уже зафиксированы, и
набор, который в них не попадает, покажет не тот цвет.

Отдай готовую таблицу девопсу — он делает из неё эталонный снапшот базы
(его задача 2), чтобы демо можно было прогнать дважды.

**Готово, когда:** по твоей таблице человек, который её не писал, воспроизводит
демо-состояние и получает те же цвета.

**Как защищать:** «Набор собран так, чтобы на одном экране были видны все четыре
состояния и обе дороги к красному. Не случайные данные — сценарий.»

## P0 — Задача 3. Третий диагноз: «отвлёкся»

**Зачем:** в `CLAUDE.md` описано три случая диагностики, в коде их два. Это
готовый ответ на «назовите слабое место» — но только если ты можешь сказать
не «мы не успели», а «вот спека, вот почему отложили».

| Признак | Диагноз | Статус |
|---|---|---|
| Есть коммиты/ревью, но задача не завершается ≥ 3 дней | `stuck` — не может | есть |
| Активности нет вообще + есть незакрытые задачи | `disengaged` — не делает | есть |
| Коммиты есть, но по не своим задачам | «отвлёкся» | **нет** |

Пробел уже зафиксирован тестом `tests/test_diagnose.py::test_distracted_case_is_not_implemented_yet`
— он проверяет текущее поведение и покраснеет, когда правило появится.

**Сделать: `docs/spec-diagnosis-distracted.md`**, коротко, но до конца:

1. **Что считается «своей» задачей.** У задачи есть `assignee_member_id`, и он
   **может быть пустым** — задача без исполнителя допустима. «Не своя» — значит
   коммит привязан к задаче, назначенной другому. Но есть ещё два случая, и по
   каждому нужно решение с обоснованием: коммит привязан к задаче **вообще без
   исполнителя** и коммит **не привязан ни к какой задаче**. Считаются они
   «отвлёкся» или нет?
2. **Порог.** Сколько коммитов не по своим задачам за неделю — уже сигнал? Доля
   или абсолютное число? Учитывая, что у команды из пяти человек за неделю
   бывает 10 коммитов, доля надёжнее.
3. **Приоритет.** Сейчас `stuck` побеждает `disengaged`. Куда встаёт «отвлёкся»,
   если признаки пересеклись?
4. **Формулировка для экрана.** Без оценки человека. Не «отвлёкся от своих
   задач», а факт: «за неделю 6 коммитов, из них 4 — по задачам других
   участников». Решение — за тимлидом, система только показывает.
5. **Тест-кейсы:** 3–4 набора входных чисел и ожидаемый диагноз. Разработке
   этого хватит, чтобы реализовать без второго захода.

**Готово, когда:** разработчик может реализовать правило, не задав тебе ни
одного вопроса.

**Как защищать:** «В ТЗ три случая диагностики, в коде два. Мы это нашли сами,
спека на третий написана, реализацию отложили ради того, чтобы один сценарий
прошёл целиком.»

Полчаса работы с открытым приложением. Пройди все экраны в трёх ситуациях:
команда без участников, участник без привязанного GitHub, участник без задач.
Запиши, где вместо честного «нет данных» показывается ноль, прочерк или пустота.
Каждое такое место — риск: тимлид примет «нет данных» за «ничего не делал», а мы
обещали обратное. Найденное отдай разработке списком.

вопрос жюри. Остальное — работа в стол.

Три файла в `docs/`, коммиты — свои, под своим именем: по критерию «вклад
